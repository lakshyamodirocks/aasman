# Contributing

Aasmaan is one Python file plus Markdown. That is deliberate: anyone can read all of it in an evening, and every change is a diff a stranger can judge.

## The one rule

**A change is done when it was run, not when it was written.** Before you open a PR:

```bash
python tests/golden.py                 # pinned behaviours — no network, no keys, ~5 s
AI_YES=1 HOME=$(mktemp -d) bash pc-setup.sh    # scripted install into a throwaway HOME
```
On Windows: `$env:AI_YES=1; .\install.ps1`. CI repeats both on Linux, macOS and Windows.

## Where things are

| File | What |
|---|---|
| `ai.py` | the whole program: brains, privacy scrub, memory, `/do` ladder, experts, self-update, daemon |
| `experts.json` + `experts/<name>/{PERSONA,KB}.md` | the 18 specialists (voice · refusals · cheat-sheet · sources) + `aasmaan` (its KB is generated by `pc/gen-selfkb.py` at build — edit the docs, not the KB) |
| `tools-routing.json` | which provider/builtin handles each `/do` capability |
| `fold-all-setup.sh`, `setup-wizard.sh`, `setup-menu.sh` | Android/Termux install, wizard, guided keys/voice/tools |
| `pc-setup.sh`, `install.sh`, `install.ps1` | Linux/macOS/WSL and Windows install + bootstraps |
| `panel.html`, `whiteboard.html` | the optional web panel served by `ai serve` (the program runs fully without them) |
| `lib/ux.sh`, `lib/probe.sh` | staged-prompt helpers and hardware probes shared by the installers |
| `tests/golden.py` | the gate |
| `docs/` | the site (GitHub Pages) and plain-language docs |

## What we say yes to

- Fixes with a golden test that fails before and passes after.
- New expert packs (copy an existing `experts/<name>/` pair; 5 Hinglish exemplars; sources with dates).
- Translations of `docs/` and installer prompts.
- Recipes in `RECIPES_PC` / `RECIPES_TERMUX` for tools people actually have.

## What we say no to

- Any dependency. `ai.py` is stdlib-only because that is the only thing that runs on a phone (Bionic libc) and the only thing a stranger can audit.
- Telemetry, analytics, "anonymous" pings of any kind.
- An install step that runs without asking.
- Code that phones a server of ours. There is none, and there will be none.

## Language

Comments and prompts are in Hinglish where the user reads them, English where only developers do. Keep it that way; do not "clean up" Hinglish into English.

User-facing strings that exist in both languages live in the `MSG` catalogue in `ai.py` (`_t("key")`); add a key there rather than a second `print`. Never translate command names, flags, env names, paths or anything shown for copy-paste — a translated command is one that fails when typed.

## How changes ship — impact radius

A change is filed under one **radius**: the set of things that can break together (first-run path, bundle build, provider ladder, pairing, one platform's installer…). The rules:

1. **One commit per radius.** Its message names the radius. Two concerns never share a commit, even when both are small — a red bisect must point at one concern.
2. **A radius carries its own paperwork, in the same commit:** the code, the golden pin that would have caught it, the `CHANGELOG.md` entry with a *Touched / Not touched* line, and any README or docs sentence that described the old behaviour. Paperwork that arrives in a later commit is the thing that drifts.
3. **Order inside a batch: smallest blast first.** A doc or first-run radius lands before a build-touching one; a harness radius never rides with an installer radius unless they are literally the same concern.
4. **Gate per commit, bundle per batch.** Every radius must pass `tests/golden.py` (and the maintainer's `check.sh`) on its own. The public bundle is rebuilt once from the batch head, must pass its own gates (scan, compile, 18/18 packs, golden inside the bundle, install into a fresh HOME), and is published in one push with one tag. `CHANGELOG.md` lists each radius in that publish, newest first.
5. **A radius that fails its gate is dropped from the batch,** not squeezed in. The batch ships without it.
6. **Where the record lives:** `CHANGELOG.md` is per radius and written for users; `VERSION` is the line installed copies compare against; the repo's maintainer log stays in the monorepo. README changes only when a behaviour a user can see changed.

Why this shape: the product is one file plus installers for three platforms, and most bugs so far were one platform's fix breaking another's assumption. Naming the blast radius up front, and shipping its evidence with it, is the cheapest way to keep that from repeating.
